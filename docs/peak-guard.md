# peak-guard：DeepSeek 高峰期智能节流

## 为什么不是普通 Skill

普通 Skill 只有在模型决定调用工具时才运行，无法在“这条群消息要不要建会话”之前拦截。
本项目在 `Orchestrator.onIncoming` 里新增了一个同步能力点 `reply.gate`：
插件返回 `{ allow:false }` 时，消息只被标记已读，不创建会话、不调用模型。

## 判定依据（诚实边界）

- 用户配置的高峰时段（本地时间，如 `9-12,14-18`，支持跨夜 `22-2`）；
- 当前模式：`off / smart / save / strict`；
- 每群每分钟、全局每分钟的滑动计数；
- `@`、命令、私聊可配置豁免。

**不知道 DeepSeek 服务器实时负载**，也不冒充知道。这里控制的是“本地观测到的预算与用户配置的高峰”。

## 行为差异

| 模式 | 拦截时机 | 输出限制 |
|---|---|---|
| off | 不拦截，只统计 | 无 |
| smart | 仅在高峰时段 | 无 |
| save | 高峰时段，预算更紧 | max_tokens 上限 |
| strict | 始终按最紧预算 | max_tokens 上限 |

默认：`smart`，高峰 `9-12,14-18`，每群 6 次/分，全局 20 次/分，输出上限 500。
`@`、`/` `!` 命令、私聊默认放行。

## 配置

插件设置页提供：启用、模式、高峰时段、仅群聊、每群/全局预算、输出上限、@/命令豁免、调试日志。

## 真实基线（2026-10-19，生产）

- 今日：prompt 23,456,334 / cached 20,171,648 / completion 117,009 / runs 598，缓存命中率 **85.99%**；
- 近 7 天：prompt 87,425,415 / cached 76,912,768 / completion 722,300 / runs 3,078，缓存命中率 **87.98%**，估算成本 ¥16.62；
- 输出 Token 占比很低（7 天 0.8%），主要成本在输入；因此节流优先减少“调用次数”，而不是压缩回复长度。

## 测试

`node --test test/peak-guard.test.mjs`：6/6 通过（时段解析、跨夜、每群预算、豁免、输出上限、off 模式）。

## 已知限制

- 没有接入 429/延迟信号：当前不会因为 API 变慢自动升级状态，需要用户配置时段或手动切 strict；
- 没有做历史消息的 token 预算裁剪（下一步）；
- 拦截是静默的（消息标已读、不回复），只写 `[peak-guard]` 日志；
- 95% 缓存目标未达成，当前 87.98%，差距主要来自每轮变化的用户上下文与群聊消息；
- 事件级去重、重试退避审计尚未完成。
